## 1. テスト概要

本書は、簡易POSアプリ（Lv1＋Lv2、小規模スーパー向け学習用アプリ）の要件定義書・設計仕様書を基準資料（Source of Truth）とし、単体テスト（UT）・結合／機能テスト（IT）・システム／E2Eテスト・UAT／受入テストの各レベルについて、実装着手後にそのままテスト実施へ移行できる品質のテストケースを整備するものである。

要求・要件定義および設計仕様の再検討・再作成は本工程のスコープに含まない。要件定義書・設計仕様書に記載のない仕様をテスト設計者が推測で確定することもしない。

## 2. テスト目的

- 要件定義書（BR/FR/SCR/DR/IF/NFR/CON/ASM）と設計仕様書（機能設計・データ設計・API設計・非機能設計）の内容が、実装後に正しく動作していることを検証できる状態にする。
- 要求・要件定義 → 設計仕様 → テスト観点 → テストケース → テストデータ → テスト実装、の対応関係（トレーサビリティ）を明確にする。
- 実装前の段階から、詳細設計相当の情報（クラス図のメソッド定義、API入出力定義）をもとに単体テストケースを具体化し、実装と並行してテストコード化（Jest／pytest）に着手できるようにする。
- 仕様上未定義の事項、要件定義書・設計仕様書の時点で未解決の`[要確認]`事項を、テスト設計の観点から可視化し、UAT／受入テストまでに解消すべき事項として管理する。

### 3.2 実装未着手であることの扱い（重要な前提の変更）

当初の想定では、実装コード・既存テストコードとの突き合わせ（「仕様 vs 実装」の差異記録）を行う予定であったが、調査の結果、本プロジェクトには実装コード・既存テストコード・Jest／pytest設定のいずれも存在しないことを確認した（2026-09-13時点）。発注者確認の結果、以下の方針で本工程を進める。

- 設計仕様書のクラス図（5.3節）・API設計（6章）・画面設計（4章）を「実装のプレースホルダー」として扱い、そこに記載された関数・メソッド・エンドポイントの入出力仕様をテスト対象の仕様として用いる。
- 「仕様・設計・実装の不一致」の確認（本来の24章相当）は、実装が存在しないため本工程では実施できない。該当する成果物（`07_仕様設計実装の不一致一覧.md`）は、実装着手後に実施すべき作業として位置づけを明記したプレースホルダーとして作成する。
- 設計仕様書自体に`[AI提案]`（要件定義書に根拠のない設計者提案）として記載されている事項（JWT有効期限、ロックアウト回数、アイドルタイムアウト時間等）は、確定要件ではないが、設計仕様書に具体的な数値が明記されているため、テストケースの前提条件・テストデータとしてはその数値を採用する。ただし期待結果の根拠欄には、当該記述が`[AI提案]`である旨を明記する。

### 3.3 テスト技法の適用方針

`input/20260909_テスト.pdf`（Tech0提供）が示す考え方を踏襲し、以下を使い分ける。

| 技法 | 主な適用対象 |
|---|---|
| 同値分割法 | 文字種・区分値（tax_category, discount_type, role等）、型不正の異常系 |
| 境界値分析 | 数量（1〜99）、金額・税率・値引率の上下限、日付（適用期間・税率適用開始日）の境界 |
| デシジョンテーブル | 値引き適用可否（会員ID入力有無×値引き対象期間内か×値引き種別）、認可判定（role×エンドポイント） |
| 状態遷移 | ログイン状態遷移、購入リストの状態（空／1件以上）、リフレッシュトークンの有効／失効状態 |
| エラー推測 | API設計書6.3節に列挙されたエラー分類（バリデーション／業務／システムエラー）をもとに補完 |

組み合わせ爆発を避けるため、`20260909_テスト.pdf`の消費税計算ワークと同様に、境界値・代表値による絞り込みを基本とし、必要な箇所（値引き×税率の組み合わせ等）ではペアワイズ的な代表組み合わせに絞り込む。「多ければよい」という考え方は取らない（詳細は各テストレベルの冒頭に記載）。

## 付録A. テストケース記載項目の定義

10〜13章（各テストレベルの詳細仕様）で使用するテストケース一覧表は、以下の項目を「ヘッダー（テスト対象ごとに共通）」と「ケース行（1ケースごと）」に分けて表現する。1ケースごとに17項目をすべて横並びにすると可読性が著しく低下するため、対象・関連要件・関連設計・テスト技法・前提条件・実行方法は対象ブロックの冒頭に記載し、ケース表は差分のある項目のみを列とする。

| 項目 | 記載位置 |
|---|---|
| テストレベル | ファイル名・見出し（UT/IT/E2E/UAT） |
| 対象 | 対象ブロックの見出し |
| 関連要件 | 対象ブロックのヘッダー |
| 関連設計 | 対象ブロックのヘッダー |
| テスト技法 | 対象ブロックのヘッダー |
| 前提条件 | 対象ブロックのヘッダー（ケースごとに異なる場合はケース表の「前提条件／備考」列） |
| 実行方法 | 対象ブロックのヘッダー |
| Test ID | ケース表 |
| テスト観点 | ケース表（「観点」列） |
| テストデータ／入力値 | ケース表 |
| 操作 | ケース表（UT/ITでは「入力値」列に統合、E2E/UATでは独立列） |
| 期待結果 | ケース表 |
| 正常／異常 | ケース表 |
| 優先度 | ケース表（P0〜P3） |
| 実行結果 | ケース表（本書では全件「未実施」） |
| 備考 | ケース表 |

優先度は以下の基準で付与する（`[AI提案]`：要件定義書・設計仕様書に優先度基準の記載がないため、一般的なリスクベースの考え方を採用）。

| 優先度 | 基準 |
|---|---|
| P0 | 確定要件（タグなし）に基づく正常系の中心的フロー。欠陥があれば業務が成立しない |
| P1 | 確定要件に基づく異常系・境界値。業務上の重要なエラーハンドリング |
| P2 | `[AI提案]`のエラー処理・非機能対策（認可、冪等性、ロックアウト等）の検証 |
| P3 | `[要確認]`事項に関連し、仕様確定後でないと期待結果が定まらないケース。現時点では設計のみ行い実施は保留 |

## 16. カバレッジ

詳細は`06_トレーサビリティマトリクス.md` 7章「カバレッジサマリ」を参照。要点は以下のとおり。

- **要件カバレッジ**: 動的テストが可能な要件（BR/FR/SCR/DR、55件）中52件に直接対応するテストケースあり（約95%）。残り3件（FR-020、DR-008、NFR-SEC-001）は仕様未確定のため部分カバレッジ
- **機能カバレッジ**: 設計仕様書3章の機能ブロックF-01〜F-08はUT/IT/E2Eで網羅。F-09（単価変更履歴記録）は間接確認のみ
- **分岐カバレッジ**: calculateAmountのrate/amount分岐、getCurrentRateの該当/非該当分岐、認可判定のstaff/admin分岐等、主要な分岐を境界値分析・デシジョンテーブルで網羅
- **異常系カバレッジ**: 各バリデーション項目に上限/下限の境界異常値・型不正・存在しないID等を網羅し、正常系のみに偏っていない
- **E2Eカバレッジ**: ログイン、商品登録（スキャン／手入力）、購入リスト操作、会員・値引き、購入確定、バーコード読み取り、管理者機能の主要業務フローを網羅

詳細は[`08_ISS管理.md`](./08_ISS管理.md)を参照。要件定義書14章・設計仕様書9章のISS一覧のうち、テスト設計に直接影響する事項を再掲する。

| ISS-ID | 内容 | テスト設計への影響 |
|---|---|---|
| ISS-002 | Lv2独自要素の画面イメージがない | E2Eテストの画面操作手順は`[AI提案]`のワイヤーフレーム案に基づく暫定手順とする |

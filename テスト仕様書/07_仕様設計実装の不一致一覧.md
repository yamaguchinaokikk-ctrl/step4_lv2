# 仕様・設計・実装の不一致一覧

## 1. 本書の位置づけ

指示に基づき、本来は「要求・要件定義」「設計仕様」「実装」の3者を突き合わせ、不一致を記録することが求められていた。しかし調査の結果、本プロジェクト（`STEP4経済産業省`）には、本書作成時点（2026-09-13）でフロントエンド／バックエンドの実装コードが一切存在しないことを確認した（`00_テスト仕様書.md` 3.2節参照）。

そのため、**「設計 vs 実装」の不一致比較は、本工程では実施できない**。発注者確認の結果、本工程では以下の対応とする。

- 「要求・要件定義 vs 設計仕様」の比較のみを本工程で実施する（2章）。
- 「設計 vs 実装」の比較は、実装着手後・単体テスト実施時に本ファイルを更新する形で行うことを次工程として明記する（3章）。

## 2. 要求・要件定義書 vs 設計仕様書の比較結果

`07_要件定義書.md`と`設計仕様書.md`を突き合わせた結果、**要件定義書の確定記述と矛盾する設計仕様書の記述は見つからなかった**。設計仕様書は要件定義書の各要件ID（BR/FR/SCR/DR/IF/NFR/CON/ASM）を出典として明示しながら設計を具体化しており、要件定義書に根拠のない事項はすべて`[AI提案]`として区別されている。

参考として、設計仕様書が要件定義書に直接の出典を持たずに独自追加した主な事項（＝要件定義書の記述と矛盾するわけではないが、要件定義書側にID化された要件が存在しない事項）を以下に整理する。これらはいずれも設計仕様書自身が`[AI提案]`または`D-ISS-xx`として明示しており、「隠れた不一致」ではないが、要件定義書側への正式な要件化（BR/FR ID付与）を検討する余地がある事項として記録する。

| 事項 | 設計仕様書上の位置づけ | 要件定義書での対応状況 |
|---|---|---|
| レジ担当者の簡易登録機能（SC-03画面、`POST /api/staff`） | `[AI提案]`、D-ISS-14（設計段階で新たに生じた検討課題） | 要件定義書に対応するFR/BR IDなし。STAFFへのデータ投入経路として設計段階で追加されたもの |
| リフレッシュトークン管理（REFRESH_TOKENSテーブル、`/api/auth/refresh`） | `[AI提案]`、D-ISS-08（解消済み：追加することで確定） | 要件定義書にはログアウト機能の実装対象化（ISS-010解消）の記載はあるが、リフレッシュトークンという実装方式自体への言及はない（実装方式は設計者に委ねられた範囲と解釈） |
| ログイン試行回数制限（ロックアウト）、アイドルタイムアウト | `[AI提案]`（具体的な回数・時間は`[要確認]`のまま） | 要件定義書に該当する要件IDなし。NFR-SEC-001（「最低限の保護が必要」という抽象的な記述）を具体化したものと位置づけられているが、具体策自体の要件化はされていない |
| BFF（Backend for Frontend）構成、金額二重検証、冪等キー | `[AI提案]` | CON-006（役割分担）を具体化したものだが、BFFという構成自体は要件定義書に記載なし |

これらはいずれも「対象外として確定した機能（14.3節）」を実装した、という意味での不一致ではなく、要件定義書が具体化していない実装方式の余白を設計仕様書が`[AI提案]`として埋めたものである。実装着手前の段階で問題視すべき矛盾ではないと判断するが、**発注者が正式な要件として確定させたい場合は、要件定義書側へのBR/FR ID付与を検討することを推奨する**（`[AI提案]`の提言）。

## 3. 設計仕様書 vs 実装の比較（次工程）

実装着手後、以下の手順で本ファイルを更新することを推奨する。

1. 実装されたクラス・関数（`Discount.calculateAmount`、`TaxService.getCurrentRate`等）のシグネチャ・戻り値・例外処理を、設計仕様書5.3節のクラス図と突き合わせる。
2. 実装されたAPIのリクエスト・レスポンス・エラーコードを、設計仕様書6章のAPI詳細仕様と突き合わせる。
3. 差異を発見した場合、以下の形式で記録する。

```
| ID | 対象（関数／API／画面） | 設計仕様書の記載 | 実装の挙動 | 差異の分類 | 対応方針（要確認／実装修正／設計修正） |
```

4. 差異が「設計のバグ（設計自体が要件定義書と矛盾していた）」なのか、「実装のバグ（設計どおりに実装されていない）」なのかを区別し、AIが勝手にどちらが正しいかを判断・修正しない。必ず発注者・開発チームへの確認事項として記録する（指示23章の方針を維持）。
5. 本書のUTケース（`01_単体テスト仕様_UT.md`）で「要確認」としたケース（丸め処理、該当なし時の挙動等）は、実装時の挙動を確認したうえで期待結果を確定し、本書・UT仕様書双方を更新する。
